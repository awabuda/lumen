# P22.5 design lock — auto-mode classifier for low-risk tool calls

> **Design-only pass.** P22.5 ships a *classifier* on top of
> the P22.0/P22.2 static permission layer. The static layer
> answers the question deterministically from a YAML rule
> list. The auto-mode classifier answers a different
> question: **for a tool call that the static layer said
> `ask`, is this call obviously low-risk enough to auto-allow?**
> P19+ rule 16 mandates a 4-framework real-URL fetch + 6-question
> audit + decision list before any code lands. The choice,
> the framework comparison, and the design constraints are all
> locked here. The first P22.5.x implementation commit is the
> next step.

**Synthesis**: Claude Code and OpenClaw both have an auto-mode shape (LLM triage in front of the human ask). LangGraph does not. Hermes is unverified. The Lumen design must commit to one of three shapes:

1. **LLM classifier** (Claude Code's path): an LLM call evaluates the prose rules and returns a decision.
2. **Rule-based classifier** (Lumen's own twist): the same deterministic engine from P22.0, but with risk-tiered defaults.
3. **Heuristic classifier**: simple "low-risk pattern" rules (e.g. "this read_file ends in `.md` and matches a known glob") without an LLM.

P22.5 picks **option 3** for the first commit. The reasoning is below.

binary "is the tool on the allow-list" gate. P22.5 is "for

### 0.3 Why P22.5 is the right slot (not P22.6 / P23+)

- **P22.6 (cross-policy imports)** is an ergonomics track;
  no other framework has a public surface for it, and the
  use case (one policy file per run) is fine for the
  single-developer default. Defer.
- **P23+ candidates** (long-term memory, computer use,
  audio) are 4-framework fetches of their own. They are
  bigger, longer, and need their own design bases. P22.5
  is the smaller, higher-leverage follow-up: it lands on
  the same shape as the static layer and reuses the same
  Zod schema.
- **Production signal exists**: P22.0/P22.2 ship with the
  P22.5 hook (`BaseToolPermissionPolicy.evaluate` already
  returns `allow | deny | ask`). A classifier that flips
  `ask` to `allow` is a one-call extension to the
  composition chain.

## 1. P22.5 core definition

P22.5 adds an **opt-in auto-mode classifier** that sits
between the static permission layer and the interrupt
middleware. The classifier is invoked **only** for tools the
static layer returned `ask` for. The classifier returns one
of:

- `allow` — the call dispatches without the interrupt layer
  seeing it.
- `ask` — the call falls through to the interrupt layer
  unchanged.
- `deny` — the call aborts with a typed `AbortError` (same
  shape as the P22.0 deny path).

The classifier is **not** an LLM call. It is a **heuristic
risk-tiered rule engine** that consumes a small
`AutoModeRules` shape from the same YAML file as the static
policy. The shape is:

```ts
type AutoModeRules = {
  /** Opt-in flag. Default: false. */
  enabled: boolean
  /** Prose rules (in plain English) for the audit log; the
   *  heuristic engine does not interpret them. */
  allowPatterns: string[]
  softDenyPatterns: string[]
  hardDenyPatterns: string[]
  /** Tool names that are NEVER auto-allowed, even if the
   *  heuristic says low risk. */
  neverAllowTools: string[]
}
```

The heuristic engine is **option 3** from §0.1: deterministic
rule-based, no LLM, no fuzzy matching. The classifier is
boring on purpose — every decision is reproducible from the
policy file + the tool call + the small heuristic table. The
P22 design doc's `every decision is auditable from a git log
of the policy file` invariant carries through.

The P22.5 first commit ships **only** the heuristic engine
and the `BaseRiskClassifier` interface. LLM-based
classifiers are an opt-in P22.7 (deferred to a separate
design basis).

## 2. P22.5 task breakdown

### 2.1 P22.5.0 — `BaseRiskClassifier` + heuristic engine

- `packages/core/src/agent/middleware/auto-mode.ts` — `BaseRiskClassifier` interface with one method `classify(toolCall, ctx): RiskClassifierDecision`. The heuristic implementation `createHeuristicRiskClassifier({ rules, riskTable })`.
- The risk table is a hard-coded map from `(toolName, argPattern)` to `low | medium | high`. P22.5.0 ships with a small starter table: `read_file: low`, `list_dir: low`, `search_files: low`, `write_file: medium` (write to a temp dir is still risky), `terminal: high` (per OpenClaw's "Safer Than YOLO" position). The table is **not** in the policy file — it is core-shipped and audited.
- 6 unit tests: low-risk call auto-allowed, high-risk call still ask, never-allow-tool always ask even with low risk, denied by softDenyPatterns, denied by hardDenyPatterns (no override), default rules.

### 2.2 P22.5.1 — composition wiring + interrupt coexistence

- New middleware `createAutoModeMiddleware({ classifier, staticPolicy })` that sits **between** the static permission layer and the interrupt layer. Composition order: `tool-permission` → `tool-permission-auto` → `interrupt` → `skill-trigger` → `plan`.
- The middleware's `wrapToolCall` re-evaluates the static policy; if the decision is `ask`, the classifier runs. If the classifier returns `allow`, the call dispatches and the interrupt layer is bypassed.
- 4 e2e tests: classifier-allow skips interrupt, classifier-ask chains to interrupt, never-allow-tool still goes to interrupt, high-risk tool still goes to interrupt.

### 2.5.2 P22.5.2 — operator experience

- The P22 policy file gains an optional `autoMode: { enabled, allowPatterns, softDenyPatterns, hardDenyPatterns, neverAllowTools }` block. The Zod schema (P22.0) gets a `discriminated union` extension: if the file declares `autoMode`, the loader accepts it; if not, the heuristic engine runs with default rules + `enabled: false`.
- A new audit row shape: `AutoModeDecisionRecord` captures the classifier's call, the risk tier, the matched rule (if any), and the final decision.
- `lumen permissions show` gains an `autoMode:` section that prints the current heuristic rules.

### 2.5.3 P22.5.3 — `lumen run --auto-mode` flag

- Composition wires `createHeuristicRiskClassifier` with the operator-supplied `autoMode: { enabled: true, ... }` block from the policy file. The flag mirrors the operator's intent: "I want auto-mode enabled for this run, with the policy file's rules".

### 2.5.4 P22.5.4 — `docs/AUTO-MODE.md` operator guide

- Three worked examples: read-only workflow (autoMode enabled, neverAllowTools=[terminal]), CI (autoMode enabled, hardDenyPatterns=["**/*.env"]), dev sandbox (autoMode enabled, softDenyPatterns reviewed and noted in audit log).
- Risk-tier table reference: which tool gets which tier by default and how to override.

## 3. 4-framework comparison

| Dimension | Claude Code | OpenClaw | LangGraph 1.0 | **Lumen P22.5** |
| --- | --- | --- | --- | --- |
| **Auto-mode shape** | LLM call against prose rules | LLM-assisted triage (per blurb; implementation 404s) | none (every interrupt is human) | **heuristic rule engine** |
| **Match surface** | prose rules (any language) | unknown (post 404s) | n/a | tool name + arg pattern + never-allow list |
| **Classifier model** | hidden LLM | hidden LLM | n/a | **none — deterministic** |
| **Audit log** | implicit (allowed action log) | Skill Card (skill-level) | full graph state | `AutoModeDecisionRecord` per call |
| **Read-from scope** | user settings + --settings + managed; **NOT project** | unknown | n/a | inherits P22.0's `defaultPermissionsPath` |
| **Override mechanism** | `"$defaults"` sentinel | unknown | n/a | `neverAllowTools` + `hardDenyPatterns` |
| **Public docs** | ✅ (settings page) | ⚠️ (blurb only) | ❌ (no auto-mode) | ✅ (this doc) |
| **Hermes parity** | n/a | n/a | n/a | n/a — unverified |

Lumen's distinct line: **deterministic heuristic, no LLM in
the runtime path**. Claude Code and OpenClaw both run an
LLM call to evaluate prose rules; Lumen does not. The
trade-off is documented: heuristic is less expressive than
prose rules, but every decision is auditable from a `git
log` of the risk table.

## 4. Key design decisions

1. **Heuristic, not LLM.** The auto-mode classifier is a
   deterministic rule engine. P22.7 (LLM classifier) is the
   next ticket for operators who want Claude Code's prose-rule
   shape.

2. **Never-allow list is opt-out-by-name.** Tools the
   operator wants to always be `ask` go in `neverAllowTools`.
   The risk table's `low` tier does not auto-allow them.

3. **Risk table is core-shipped, not policy-shipped.** The
   table is small and audited as part of the framework. Moving
   it to the policy file would let a malicious repo weaken
   the default risk tier (same threat model as Claude Code's
   "ignored in project settings" decision for the auto-mode
   classifier).

4. **Auto-mode is opt-in via `enabled: true` in the policy
   file.** The default is `enabled: false`. This matches
   P22.0's `default: ask` posture: the static policy is the
   baseline, the classifier is an opt-in enhancement.

5. **Composition order**: `tool-permission` →
   `tool-permission-auto` → `interrupt` → `skill-trigger` →
   `plan`. The `tool-permission-auto` middleware **short-circuits
   the interrupt layer** on `allow` — this is the one place
   where P22.5 *does* short-circuit the inner chain, unlike
   P22.0 (which lets the inner chain run on `allow` / `ask`).
   The rationale: a heuristic `allow` is the operator's
   explicit opt-in ("auto-allow low-risk calls") and the
   interrupt layer would defeat the purpose.

6. **Audit row always records the call.** Even when the
   classifier returns `allow`, the decision lands in the
   state slice so `lumen permissions show --audit` can
   print the recent auto-allowances.

## 5. Open questions (P22.5.0 implementation)

- **Risk-table override**: should the operator be able to
  re-tier a tool? (e.g. "I trust my `terminal` tool; treat
  it as `medium` not `high`.") Claude Code's prose rules
  do this naturally; Lumen's heuristic table does not.
  **Decision: defer to P22.7. P22.5 ships with the core
  table only.** If operators start asking, the override
  lives in the policy file's `autoMode: { overrides }`
  block.

- **Soft-deny / hard-deny split**: Claude Code distinguishes
  "soft deny" (override-able by LLM reasoning) from "hard
  deny" (always). Lumen's heuristic engine has no LLM
  reasoning layer. **Decision: keep both, treat them
  identically in P22.5; the split is a placeholder for the
  P22.7 LLM classifier.**

## 6. Risk + mitigation

| Risk | Mitigation |
| --- | --- |
| Heuristic mis-classifies a high-risk call as low | Never-allow list + hardDenyPatterns + high-tier (terminal) keep the safety net. The `lumen permissions show --audit` command lists recent auto-allowances. |
| Operator forgets the `auto-mode` is enabled | The audit log + a `lumen permissions show` red-flag row (`auto-mode is enabled`) catch this. The startup banner in `lumen run --auto-mode` prints the current heuristic table. |
| Composition ordering bug | Integration test pins the order (permission → permission-auto → interrupt). |
| Risk-table widening (P22.7) breaks the invariant | P22.7 keeps the heuristic as the fallback when the LLM call fails or is disabled. The P22.5 surface is preserved. |
| OpenClaw's "Safer Than YOLO" post is still 404 when P22.5 ships | Re-fetch in P22.5.0 implementation; if still 404, cite the blurb verbatim (already done in this doc). |
