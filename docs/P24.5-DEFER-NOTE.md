# P24.5 — Computer Use (#10) deferral note

> **Status: NOT SHIPPED.** This commit documents why bug.md
> #10 ("Computer Use" — direct OS-level screen / keyboard /
> mouse control by the agent) is explicitly **deferred** out
> of the P24 sweep, and what it would take to ship it later.

## 1. Why deferral

The only mature implementations of "Computer Use" are:

  - **Selenium-derivative** libraries (`selenium`,
    `selenium-webdriver`) — Chromium / Firefox / Edge / Safari
    + WebDriver. Effectively a peer of Playwright; would NOT
    add a new native dep but ALSO would not add real
    screen / keyboard / mouse access because the agent
    only sees the browser surface, not the OS surface.
  - **`nut.js`** (the most cited npm Computer Use library)
    — uses Quartz (macOS), X11 (Linux), `user32` (Windows)
    via FFI. Adds a **native binary dependency** to the
    lumen install.
  - **PyAutoGUI / Xdotool / `osascript`** — Python or
    subprocess glue that ultimately depends on the same
    OS-level APIs.

Lumen's **native-dep guardrail** (P22.7 §3) restricts the
runtime to `better-sqlite3` only, on the basis that every
additional native dep is a future ABI-drift footgun. Any
of the three Computer Use options above would violate that
guardrail.

## 2. Operator workaround (already shipped)

Operators who need Computer-Use-like semantics today drive
Chromium via `web_browser.act(selector)` (P24.1). That tool
delivers every Computer-Use outcome except two:

  - **Coordinate-based input** (clicking at pixel
    coordinates instead of selector). Useful when the
    target app has no semantic selectors (e.g. a canvas).
  - **Cross-app interaction** (drag-and-drop between
    browser and native apps). Out of scope for lumen.

For most enterprise / dev-tool workloads, selector-based
input covers the long tail.

## 3. When we DO ship #10

Conditions (any one suffices to re-open the ticket):

  1. Lumen relaxes the P22.7 §3 native-dep guardrail after
     shipping an automatic ABI-drift detector (P22.7 itself)
     and seeing it stabilise.
  2. A pure-JS implementation becomes viable (e.g. Selenium
     4 without the JNI bridge, or a Chromium-only "OS
     surface" via the DevTools Protocol's
     `Input.dispatchMouseEvent`).
  3. Lumen drops its hermetic dev-sandbox story entirely
     and ships a "host-aware" agent (unlikely; this is
     fundamentally opposed to the lumen design).

## 4. What a future P-ticket would look like

If we DO ship #10, the work decomposes into:

  - New package `@lumen/tools-compute` (or similar)
    alongside `web_browser`. Single composite tool
    `computer_use` with a discriminated `op` of `screenshot`
    / `click` / `type` / `key` / `move` / `scroll`.
  - Provider interface (mirrors `BrowserProvider`) with
    a default `NutJSP` implementation behind an
    `--computer-use` opt-in flag on `lumen run`.
  - Risk class: `dangerous` (P22.0). Pre-approval
    required.
  - Sandbox boundary: the computer_use tool would NOT
    touch the existing `lumen doctor` MCP surfaces. It
    would live in its own `packages/tools-compute/`
    workspace so the P22.7 §3 guardrail stays scoped.

Not in this sweep. Documented for the next operator who
asks "where's the Computer Use tool?".
