# P22.6 design lock — cross-policy imports (multi-file composition)

> **Design-only pass.** P22.6 lets the operator split the
> tool-permission policy into multiple files and compose
> them at load time. P19+ rule 16 mandates a 4-framework
> real-URL fetch + 6-question audit + decision list before
> any code lands. The choice, the framework comparison,
> and the design constraints are all locked here. The first
> P22.6.x implementation commit is the next step.

## 0. Why P22.6

### 0.1 4-framework fetch verification (2026-07-13)

| Framework | URL fetched on 2026-07-13 | Key takeaway for P22.6 |
| --- | --- | --- |
| **Claude Code** | `https://docs.claude.com/en/docs/claude-code/settings` (re-fetched 2026-07-13) | **Multi-scope settings with merge semantics**: managed (highest, server-managed) → user → project → local. Each scope is a separate JSON file. **Permission rules merge across scopes** (not override); arrays de-duplicate, objects deep-merge. **Numeric prefix ordering** for the drop-in directory pattern: `10-telemetry.json` < `20-security.json`. **Managed-only lockout**: `allowManagedPermissionRulesOnly` prevents user/project from loosening the rules — the security boundary. This is the direct precedent. |
| **OpenClaw** | `https://openclaw.ai/blog` (re-fetched 2026-07-13) | No public surface for cross-policy composition. The blog has posts on "Safer Than YOLO" (auto-mode), skill security, and security roadmap, but nothing on policy composition. The OpenClaw config lives at `~/.openclaw/openclaw.json` as a single file. **No precedent.** |
| **LangGraph 1.0** | `https://docs.langchain.com/oss/python/langgraph/interrupts` (re-fetched 2026-07-13) | No policy file at all. `interrupt()` is a runtime call. **No precedent.** |
| **Hermes Agent** | `https://hermes-agent.nousresearch.com/docs/` (re-fetched 2026-07-13) | No public surface. **Unverified.** |

**Synthesis**: Claude Code is the only framework with a
public, documented multi-scope policy composition model.
OpenClaw is a single file; LangGraph has no policy; Hermes
is unverified. P22.6 follows Claude Code's shape: a static
file graph (managed → user → project → local) with merge
semantics, with a managed-only lockout to keep the security
boundary.

### 0.3 Why P22.6 is the right slot (not P23+)

- **P22.6 has direct precedent** (Claude Code). P23+
  candidates (Memories, Computer use, Audio) are 4-framework
  fetches of their own.
- **Composition unblocks enterprise use cases** without
  breaking the P22.0/P22.5 invariants.
- **The risk table, never-allow list, and hardDeny patterns
  all compose cleanly** when split by file. P22.5's
  heuristic engine does not need a single-file guarantee.

## 1. P22.6 core definition

P22.6 lets the policy file declare an optional `imports:`
list. The composition root walks the import graph in
topological order and merges the rules / autoMode block /
hardDeny patterns / neverAllowTools.

The merge semantics mirror Claude Code:

- **Rules**: deep-merged. `default` and `version` are
  taken from the *root* policy. The imported file's `default`
  is ignored (one default per policy graph). The imported
  file's `rules` array is appended after the root's rules
  (first match wins; the import order is the rule order).
- **autoMode block**: replaced by the imported file's
  block. The last import in the list wins. The rationale:
  autoMode is a single config block, not a list.
- **neverAllowTools**: arrays are concatenated and
  de-duplicated.
- **hardDenyPatterns**: arrays are concatenated.
- **allowPatterns + softDenyPatterns**: concatenated.

A circular import is a parse error (typed `ConfigError`).
A missing import path is a parse error. A relative import
path is resolved against the importing file's directory.

The composition root's invocation is unchanged: the
operator passes a single `--permissions <path>`. P22.6
extends the loader to follow the import graph before
returning the merged policy.

## 2. P22.6 task breakdown

### 2.1 P22.6.0 — `imports:` block + loader extension

- `apps/cli/src/permissions-loader.ts`: `loadPermissionPolicyFromFile(path)` now follows the `imports:` list. The function returns a single `ToolPermissionPolicy` with the merged shape.
- The Zod schema (`ToolPermissionPolicySchema`) gains an optional `imports: z.array(z.string()).default([])`. The Zod schema is recursive in the sense that the imported files share the same shape.
- A small `mergePolicies(roots, imports)` helper does the deep merge. Cyclic detection: a `Set<string>` of visited absolute paths; revisit → throw `ConfigError('circular policy import: <path>')`.
- 6 unit tests: simple import, deep import chain, cycle detection, missing file, rule ordering (imports come after root), neverAllowTools de-duplication, hardDenyPatterns concatenation.

### 2.2 P22.6.1 — managed-only lockout (security boundary)

- The policy file gains an optional `allowOverrides: boolean` block (default `false`). When `false`, the import graph is **trust-preserving**: a user/project import cannot loosen a rule that the root policy denies.
- The merger sorts the rules by source (managed → user → project → local) and applies the `lockDenyRules: true` policy: a `deny` in any earlier file wins over an `allow` in a later file.
- 4 e2e tests: import loosens rule but lockout wins, import is allowed, missing lockout flag is permissive, multiple denies from different files all win.

### 2.3 P22.6.2 — `lumen permissions show` with imports

- The `lumen permissions show` command prints a `from <path>` line for each rule in the merged policy. The operator can see which file each rule came from.
- `--json` output gains a `_sources` map (rule name → source file path) for the audit log.
- 2 e2e tests: human-readable output includes source paths; JSON output has the `_sources` map.

### 2.4 P22.6.3 — `lumen permissions audit` (decision log viewer)

- New subcommand `lumen permissions audit [--session <id>] [--db <path>] [--json]` reads the auto-mode + permission state slice from a checkpoint database and prints the recent decisions.
- 2 e2e tests: human-readable output, JSON output.

### 2.5 P22.6.4 — `docs/PERMISSIONS.md` extension

- New section: "Composing policies across files". Worked example: a managed policy + user policy + project policy.
- Cross-reference to `docs/P22.6-DESIGN.md`.

## 3. 4-framework comparison

| Dimension | Claude Code | OpenClaw | LangGraph | **Lumen P22.6** |
| --- | --- | --- | --- | --- |
| **Multi-file model** | managed → user → project → local; each is a separate JSON file | single file | no policy | **static `imports:` list, topological walk** |
| **Merge semantics** | rules merge across scopes; arrays de-dupe; objects deep-merge | n/a | n/a | **rules appended; autoMode replaced; arrays concat + dedupe** |
| **Ordering** | numeric prefix (`10-x`, `20-y`) | n/a | n/a | **list order (root first, then imports in order)** |
| **Security boundary** | `allowManagedPermissionRulesOnly` prevents user/project from loosening managed rules | n/a | n/a | **`allowOverrides: false` (default) + lockDenyRules** |
| **Cyclical imports** | no equivalent | n/a | n/a | **typed `ConfigError`** |
| **Audit (which file?)** | implicit (settings hierarchy) | n/a | n/a | **`_sources` map + `lumen permissions show`** |
| **Public docs** | ✅ | ⚠️ (single-file only) | ❌ | ✅ (this doc) |
| **Hermes parity** | n/a | n/a | n/a | n/a — unverified |

Lumen's distinct line: **a single file path at the
`--permissions` flag**, with a manifest of imports. Claude
Code uses filesystem-level scope (multiple files always
present); Lumen uses file-level composition (the operator
opts in to imports). The simpler model fits the P22
"operator-driven, deterministic, auditable" design.

## 4. Key design decisions

1. **One path, many files.** The `--permissions` flag
   takes a single path. Imports are declared inside the
   file. The CLI does not accept a directory of policies.

2. **The import graph is static.** No conditional imports,
   no glob imports, no remote URLs. P22.6 is a list of
   string paths; that's it.

3. **The default is `allowOverrides: false`.** An operator
   who wants to compose a managed policy with a user policy
   gets the secure-by-default merge: a deny in the root
   wins over an allow in the import.

4. **`autoMode` is a single config block, not a list.** The
   last import's `autoMode` block wins. The rationale: an
   autoMode block is a single classifier configuration; if
   you need different autoMode rules for different call
   sites, use the per-tool `neverAllowTools` opt-out.

5. **Cyclic imports are a typed error.** The composition
   root refuses to start. P22.0's `ConfigError` shape
   carries the cycle path for the operator.

6. **The audit log records the source file** for every
   decision. P22.6 ships `lumen permissions audit` to read
   the log from a checkpoint database.

## 5. Open questions (P22.6.0 implementation)

- **Order of import resolution**: the design says
  "topological" but the implementation will be a simple
  `for (const path of imports) await loadPolicy(path)`
  loop. The cycle detection (`Set<string>` of visited
  absolute paths) catches cycles at any depth. **Decision:
  no topological sort; linear walk with cycle detection.**
  Imports are ordered by the operator's list.

- **Wildcard imports**: Claude Code uses `*` in some
  scopes. Lumen's P22.6 does not. **Decision: defer to
  P22.7 (LLM classifier follow-up).** Wildcards add a
  globbing layer; P22.6 keeps the surface tight.

- **Remote imports**: `import: 'https://example.com/policy.yaml'`.
  **Decision: out of scope for P22.6. The loader is
  fs-only.** P22.8+ would handle remote imports.

## 6. Risk + mitigation

| Risk | Mitigation |
| --- | --- |
| Cyclic import hangs the loader | `Set<string>` of visited absolute paths; revisit throws `ConfigError`. |
| Operator forgets `allowOverrides: false` and silently weakens security | The default is `allowOverrides: false`. `lumen permissions show` red-flags the flag in the resolved view. |
| Path traversal in import strings | Imports are resolved against the importing file's directory; absolute paths are allowed but logged. A future P22.6.x can add a `baseDir` constraint. |
| A malicious repo weakens the autoMode block | The composition root treats `autoMode` as a single block; the operator can opt to keep `autoMode` only in the managed file by not declaring it in the project file. |
| Source-path tracking drifts across rule edits | The `_sources` map is recomputed on every load. A future P22.6.x can add a `--strict-sources` flag that fails the load if a rule's source file does not exist. |
